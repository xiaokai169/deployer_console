# Deploye 发布控制台

基于 **Electron + Vue 3 + TypeScript** 的项目发布桌面应用。支持多项目、项目下测试/生产环境、共享服务器连接、SFTP / rsync 传输、原子软链切换、发布历史与回滚。

## 功能

- 多项目配置：基本信息、构建命令、产物校验、发布策略
- 服务器管理：集中维护 SSH 连接（密钥 / 密码），可被多个项目的多个环境复用
- 项目 → 环境（测试 / 生产）→ 服务器：环境选择服务器，并独立配置根目录、保护路径（跳过 / 软链共享 / 从上一版本复制）、钩子
- 环境级构建：构建命令、产物目录、构建环境变量、自动发布分支，支持测试/生产按分支分别构建部署
- 一键操作：`预检` / `仅构建` / `选快照发布` / `构建并发布` / `回滚` / `取消`
  - `构建并发布`：先确认目标环境与服务器，再构建 → 生成产物快照 → 按环境发布
  - `选快照发布`：从历史产物快照中选择一份发布，**不再读取本地 dist**，避免把上一次构建（可能属于别的环境）的产物发错
- 产物快照：每次构建结束后把 dist 固化为只读快照（记录分支 / commit / 构建命令 / 环境变量指纹 / 目标环境），部署只从快照读取；快照与目标环境构建配置不一致时会在确认弹窗与日志中提示
- 发布确认：发布前展示「环境 / 服务器 / 部署目录 / 产物」对照表，生产环境需二次勾选确认
- 发布流水线：构建 → 校验 → 文件清单 → 产物快照 → 打包 → 上传 → 远端解压 → 保护路径 → 钩子 → 原子软链切换 → 清理
- SFTP 上传（支持压缩包或逐文件）与 rsync 增量同步
- 本次变更预览（新增 / 更新 / 删除）、发布历史与按版本回滚
- 实时日志（级别过滤 / 导出 / 清空）、阶段进度
- 内置 10 套主题（深色 / 浅色 / 现代风格），顶栏即时切换并记忆选择
- 多环境并发、失败策略（停止 / 继续 / 自动回滚）、超时与重试
- 部署互斥锁：同一目标目录同一时刻只允许一个发布 / 回滚流程，冲突时停止并提示占用人
- 团队配置仓库：通过 SSH 集中共享项目配置，列表可见项目名，内容需团队密码才能解密
- Git 自动发布：监听 main / master 主分支，发现新提交后自动构建并发布（可开关）
- 独立工作区构建（git worktree）：自动发布不切换、不改动当前分支与工作区，锁文件变化时自动安装依赖

## 技术栈

| 模块 | 方案 |

## 开发与构建

```bash
npm install          # 安装依赖
npm run dev          # 开发模式
npm run typecheck    # 类型检查
npm run build        # 类型检查 + 构建
npm run dist:win     # 构建 Windows 安装包（输出 dist/）
npm run release:win  # 构建并上传到 GitHub Releases（需要 GH_TOKEN）
```

## 版本更新（自动更新）

客户端启动 20 秒后自动检查 GitHub Releases，之后每 4 小时检查一次；发现新版本会在后台下载，顶栏版本号实时显示进度。下载完成后点击顶栏版本号，选择「立即重启安装」即可完成更新。

### 首次配置

更新源已指向 `xiaokai169/deployer_console`。发版机器只需准备一个有 `repo` 权限的 GitHub Token（如果已登录 GitHub CLI，可直接 `export GH_TOKEN=$(gh auth token)`）。

### 发版步骤

```bash
# 1. 递增版本号（直接改 package.json 的 version，git 仓库中也可用 npm version patch）
# 2. 设置 Token 后构建并发布
#    Git Bash（已登录 gh CLI 时可直接复用）：
GH_TOKEN=$(gh auth token) npm run release:win
#    PowerShell：
$env:GH_TOKEN=(gh auth token); npm run release:win
```

`release:win` 会把安装包、`latest.yml`、`.exe.blockmap` 上传到对应版本的 GitHub Release。**三者必须在一起**，客户端依赖 `latest.yml` 判断版本并校验安装包。

### 注意事项

- 每次发版必须递增 `version`，相同版本号客户端不会提示更新
- 应用默认未做代码签名，Windows 安装时会出现 SmartScreen 提示（可选择继续安装）；正式对外分发建议配置签名证书
- 开发模式（`npm run dev`）不检查更新，只有安装打包版本后才生效
- 更新前若正在执行发布任务，重启安装会中断任务，请在空闲时更新

> 国内网络安装 Electron 时可设置镜像：`ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/`

测试或便携运行时可指定独立配置目录，避免污染正式配置：

```bash
DEPLOYE_USER_DATA=F:/deploye/.test-userdata npx electron .
```

## 服务器端约定

服务器需为 Linux（或兼容 GNU 工具链），并具备：

- `ssh` 可登录，部署用户对根目录有写权限
- `tar`、`find`（支持 `-printf`，不支持时会降级为 `ls`）、`ln`、`bash`
- 目录结构（相对根目录）：

```
/var/www/my-app/
├─ releases/20261112-092033/   # 每次发布一个版本目录
├─ uploads/                    # tar.gz 上传暂存，解压成功后立即删除
└─ current -> releases/20261112-092033
```

- `current` 是软链，`ls -l current` 可以看到箭头；部分 FTP / 文件管理器会把它显示成目录
- `uploads` 仅作为解压暂存：tar.gz 解压成功后立即删除；解压失败时保留，便于排查

- 切换使用 `ln -sfn`，Linux 上为原子操作；`current` 若已是真实目录会切换失败，需先手工处理
- 保护路径规则：
  - `跳过`：在打包 / rsync 时排除，版本目录中不出现
  - `软链共享`：将 `<根目录>/<路径>` 软链到 `<版本目录>/<路径>`，所有版本共用同一份
  - `从上一版本复制`：在切换 `current` 之前，把上一个生效版本中的同名文件 / 目录用 `cp -a` 复制到新版本目录（先删除新版本中的同名内容）；首个版本无上一版本时自动跳过。放在切换前完成，避免线上短暂缺文件
- 部署互斥锁：
  - 发布 / 回滚前在 `<根目录>/.deploye.lock` 原子创建锁（`mkdir`），同一目录同一时刻只允许一个发布流程
  - 已被占用时直接停止，提示占用人、主机、项目、版本、开始时间
  - 持锁期间每 45 秒心跳更新；超过 10 分钟无心跳视为过期锁，自动清理后重试一次
  - 确认对方异常退出时可手动解锁：`rm -rf <根目录>/.deploye.lock`
  - 切换 `current` 前会再次校验它未被其他操作修改，变化则中止且不切换
  - 锁只能防住其他 Deploye 实例；手动登录服务器改文件无法可靠检测，但 `current` 被改动会中止发布

## 项目 → 环境 → 服务器

- **服务器**（右上角「服务器管理」）：只保存 SSH 连接信息（名称、主机、端口、账号、密钥/密码），可被多个环境复用；连接测试、修改、删除都在这里
- **环境**（项目下，默认「测试环境」「生产环境」）：选择一台服务器，并配置：
  - 根目录与目录结构（uploads / releases / current / 保留版本数）
  - 保护路径、发布钩子
  - 环境级构建：构建命令、产物目录、构建环境变量（每行 `KEY=VALUE`）
  - 自动发布分支（如 `develop` / `main`）与「参与 Git 自动发布」开关
- **发布选择**：右侧环境卡片勾选哪些环境就操作哪些

行为：

- **手动发布**：勾选环境即发布到对应服务器/根目录；不同环境的构建配置不同时，按配置分组分别构建、分别部署
- **仅构建**：使用已勾选环境（未勾选时用当前选中的环境）的构建配置
- **Git 自动发布**：环境配置了自动发布分支时按分支独立触发（`develop` → 测试、`main` → 生产）；都未配置时使用项目全局分支，并发布到所有参与自动发布的环境
- 同一服务器不同根目录、不同服务器相同根目录都支持；部署锁、releases、current 均按环境根目录隔离
- 旧版配置会自动迁移：原「目标服务器」拆成一个服务器连接 + 一个同名环境，发布历史与密钥保留

## 团队配置仓库

不用互发文件，通过一台 SSH 服务器集中共享项目配置：

- 左栏「团队配置」→「连接设置」，连接方式二选一：
  - **使用已配置的服务器（推荐）**：直接从下拉中选择服务器连接，复用它的 SSH 账号与密钥/密码，不再重复填写或验证
  - **自定义连接**：为独立的配置服务器填写主机、端口、账号、自己的密钥/密码
  - 仓库目录默认 `~/.deploye-config`；保存一次后，获取 / 发布都会自动复用该连接
  - 连接信息与密钥口令只保存在本机（`safeStorage` 加密），**永远不会随项目配置共享**
  - 每个人使用自己的 SSH 账号和密钥访问仓库；关联的服务器被删除时会提示重新选择
- 「发布配置」：选择当前项目，设置团队配置密码后上传
  - 使用 `scrypt + AES-256-GCM` 加密整个项目配置，密码不落盘
  - **不包含**任何密码、密钥口令或密钥文件
  - 每个项目一个文件，同名重新发布会覆盖
- 「获取配置」：
  - 验证连接后列出仓库中的项目名、发布人、更新时间、环境数
  - 选择项目 → 输入团队配置密码 → 解密并导入（重新生成 ID；本地路径/密钥缺失会提示）
- 安全模型：
  - 看到项目列表需要有仓库的 SSH 访问权限
  - 解密配置必须知道团队配置密码；密码错误或被篡改会被认证标签校验拒绝
  - 仓库文件仅 `meta`（项目名、发布人、时间、环境数）是明文，其余全部在密文中
- 仓库连接配置属于本机设置，不会随项目配置共享

## Git 自动发布

在项目配置的「Git 自动发布」Tab 中开启后，应用会周期性监听本地仓库的远程跟踪分支：

- 触发来源二选一：
  - **仅本机推送（默认）**：只响应你在本仓库执行的 `git push`（依据 reflog 中 `update by push` 记录），同事推送、`fetch`、`pull` 都不会触发，也不会执行定时 fetch
  - **任意人推送**：定时 fetch 主分支，任何人推送都会触发。多台机器/多个人同时开启会重复构建发布，建议只保留一台
- 分支来源：环境配置了「自动发布分支」时按分支独立监听（如 `develop` → 测试、`main` → 生产）；都未配置时使用项目全局分支（远程名、间隔可配置）
- 检测到**新的已推送提交**后，只发布该分支关联的环境，并按各环境的有效构建配置分组构建（构建 → 校验 → 打包 → 上传 → 切换）
- 环境关闭「参与 Git 自动发布」后不会参与自动发布，只能手动发布
- 首次开启只记录基线，不会立即发布
- 独立工作区模式（默认开启）下从该提交检出构建，不要求你当前 HEAD 在该提交上；关闭独立工作区时，要求当前工作区 `HEAD` 等于触发提交，否则跳过并提示
- 切换「触发来源」会清空监听基线，重新记录，不会立即发布
- 已有任务执行中时不会并发触发，会在后续检查中重试
- 应用运行期间关闭开关会清空监听基线，再次开启时重新记录基线
- 处理过的最新提交 SHA 会持久化，应用重启不会重复发布同一提交

前提：本地项目目录是 Git 仓库，已配置远程，且本机具备 fetch / push 凭据（`GIT_TERMINAL_PROMPT=0`，不会弹窗要密码）。

### 独立工作区构建（默认开启）

开启「使用独立工作区构建」后，自动发布不会切换你的分支，也不会改动当前工作区：

1. 首次：`git worktree add --detach <userData>/workspaces/<项目ID> <提交>`；后续复用并 `checkout --force --detach` + `clean -ffd`（保留 node_modules 等被忽略文件）
2. 存在 `.gitmodules` 时自动更新子模块
3. 「构建前复制文件」中的路径（如 `.env`）从当前工作区复制到部署工作区
4. 按锁文件自动选择 `npm ci` / `pnpm` / `yarn` / `bun` 安装依赖；锁文件未变化则跳过
5. 在部署工作区内执行构建命令并走正常发布流水线

注意：

- 首次发布需要检出代码并安装依赖，耗时会明显增加
- 部署工作区位于应用数据目录，占用额外磁盘空间；可在界面「清理工作区」
- 复制的是**当前工作区**里的文件，不保证与触发提交一致（例如你在其他分支改过 `.env`）
- 关闭「保留部署工作区」时，发布成功后会清理工作区；失败时保留便于排查
- 仓库需要 git ≥ 2.5，且本机已正确安装 git

## 安全说明

- 渲染进程开启 `contextIsolation`、关闭 `nodeIntegration`，仅通过 preload 白名单 IPC 访问能力
- 密码 / 密钥口令使用 `safeStorage` 加密落盘，读取时不会下发到渲染进程
- 远端命令中的路径均做 POSIX 单引号转义
- 当前版本未做 SSH 主机指纹校验（默认接受主机密钥），生产环境建议后续接入 `known_hosts` 校验

## 已知限制

- rsync 仅支持密钥认证；需本机安装 rsync；Windows 下 cwRsync 的本地路径格式可能需调整
- 操作员 / 发布人自动取项目本地仓库的 `git config user.name`（未设置时回退系统用户名），无需手工填写；发布历史中的记录随发布机器不同而不同
- 「本次变更」基于上一次发布成功时记录的文件清单对比
